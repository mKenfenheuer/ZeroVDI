Verdict

ZeroVDI has the bones of a serious product: server-side credential injection that never reaches the browser, a full RDPGFX pipeline with ClearCodec, RemoteFX Progressive and H.264, a working clone-on-connect broker with a safe-destroy invariant, encrypted secrets, audit and recordings, and an admin UI built from consistent shared parts. What separates it from a professional VDI platform today is not one missing feature but a layer of unfinished edges: rendering choices that make WebKit crawl, a device policy that is enforced in the UI but not in the relay, an NLA handshake that skips the one check that justifies accepting any host certificate, a broker with no reconciler, keyboard handling that drops arrow keys, and several capabilities that the documentation describes as shipped but that the code stubs out.

Safari performance root-caused

Per-tile blits out of a CPU-backed canvas, no frame pacing, acks sent before decode. Fixable in the client alone.

Browser RDP client gaps

GFX codecs are strong; keyboard, pointer types, clipboard formats, touch and multi-monitor are not.

Gateway protocol gaps

Relay is a clean byte pump. CredSSP server binding unverified; recorder corrupts bidirectional DVC streams.

VDI broker incomplete

Dedicated pools work. Floating, guest-agent identity, domain join, reconciliation and idle handling for clones do not exist.

Security & ops gaps

Good crypto at rest; missing headers, host-header poisoning, dead NT-hash storage, no tests, root container, single instance.

Admin UI solid base

Consistent, safe CRUD with provenance badges. Lacks a real operations dashboard, test buttons, a setup path, and user lifecycle actions.

End-user UX solid base

Preflight stepper and reconnect flow are good. Preflight hides the clone phase; toolbar is thin; no touch; docs promise more than the client does.

Start here
  1. Fix the client render path so Safari (and every other browser) paints once per frame instead of once per tile, and acknowledge frames only after they are decoded. This is the Safari fix and also removes the lag-balloon behaviour everywhere.
  2. Enforce device policy in the relay, not only in the form. Today a modified client joins clipboard, audio, microphone and camera channels regardless of a Disabled policy, while comments in the code claim the relay clamps.
  3. Verify the CredSSP server binding and adopt a host-certificate policy. The gateway accepts any TLS certificate on the promise that CredSSP detects a man-in-the-middle, but the server's public-key confirmation is never checked.
  4. Add a broker reconciler and bring clones under lifecycle management. A restart mid-clone leaves the user's desktop stuck forever; clones are never idle-suspended; failed clones leak VMs.
  5. Make the docs and the option lists truthful. Floating pools, guest-agent identity, domain join, hostname patterns and the Kerberos fields are selectable or documented but not implemented.

Safari slowness

The client runs the exact same pipeline in every browser. There is no user-agent or capability detection anywhere in the client, and no requestAnimationFrame at all: every paint happens synchronously inside the WebSocket onmessage handler. Chromium's Skia software canvas tolerates that design; WebKit's CoreGraphics backend does not. The causes below are ranked by how much of the observed slowness they plausibly explain.

What Safari actually executes

  1. Default display mode is H.264 (Models/ConnectionDefaults.cs:31). The H.264 frame is decoded in decode-worker.js via WebCodecs and the VideoFrame is transferred to the main thread.
  2. The main thread draws it into a surface OffscreenCanvas created with willReadFrequently: true (rdpgfx.js:640), which pins that canvas to CPU memory. A GPU-backed VideoFrame painted into a CPU canvas is a full readback plus a colour conversion, every frame.
  3. The surface is then blitted to the visible canvas, once per region. For H.264 the region list is ignored and the whole frame is blitted (rdpgfx.js:1244-1257). For RemoteFX Progressive, which GNOME Remote Desktop and many Windows hosts send, every 64×64 tile gets its own putImageData and its own drawImage to the output (rdpgfx.js:947-953 feeding rdpgfx.js:1315-1338). Two hundred tiles means four hundred canvas operations before the next WebSocket message can be handled.
  4. At END_FRAME the client immediately sends FRAME_ACKNOWLEDGE with queueDepth = 0 and a QoE ack (rdpgfx.js:753-790), before any of the queued worker decodes have landed. The host therefore believes the client is keeping up and keeps streaming at full rate.

A separate Safari failure mode that looks like "slow"

If VideoDecoder rejects the H.264 configuration (there is no isConfigSupported probe, and no hardwareAcceleration hint, decode-worker.js:242), the worker sets unsupported and silently drops every later frame (decode-worker.js:250-257). The user sees a black or frozen desktop, not an error, and there is no fallback to Progressive or ClearCodec. Capabilities are advertised before the decoder is ever probed (protocol.js:2409, rdpgfx.js:401-459).

Fixes, in payoff order

  1. Coalesce output blits. Make _afterSurfaceUpdate only accumulate into the per-surface dirty rectangle, then flush one union blit per surface at END_FRAME, and via a single requestAnimationFrame for H.264 frames that arrive outside a frame. This alone changes the progressive path from 400 canvas operations per PDU to one.
  2. Remove willReadFrequently from surface canvases and gate the black-cache scan behind the diagnostic flag. For the ClearCodec glyph snapshot, keep the composite in JavaScript (glyphs are at most 1024 pixels) so no production getImageData remains.
  3. Paint H.264 frames directly to the output canvas when a surface is mapped 1:1 to the output. The unused _onGfxDirectFrame hook at client.js:1345-1358 already exists for this. Honour the AVC420 region list instead of blitting the full frame.
  4. Real backpressure. Send FRAME_ACKNOWLEDGE from the decode-settled path with the actual queue depth, and drop to the latest frame when the backlog exceeds a small number of frames. The changelog notes an earlier experiment with an up-front SUSPEND that stalled the host; a per-frame ack with a truthful depth is the middle path mstsc uses.
  5. Probe before advertising. Run VideoDecoder.isConfigSupported for the intended profile in both window and worker before CAPS_ADVERTISE; fall back to a Progressive-only capability set when it fails, and add an "Auto" display mode that does this by default.
  6. Move ZGFX and ClearCodec into the worker once the paint path is fixed.
  7. Coalesce mousemove to one event per animation frame, cache the bounding rectangle, use passive listeners, and flush held keys on blur.
  8. Cap HiDPI at a 200% scale factor and 3840×2160 unless the user opts in.
  9. Implement requestKeyframe (referenced at rdpgfx.js:196, 1775 but undefined) using the existing sendRefreshRect, and surface the "unsupported" state as an error with automatic fallback.
  10. Gateway stopgap: a user-agent aware default display mode for WebKit and an optional frame-ack hold-back knob would buy time, but neither substitutes for the render-path fix.

Not the cause: WebSocket binaryType is correctly arraybuffer; VideoFrame and ImageBitmap objects are closed on every path; the ordered-decode barrier always settles; diagnostic logging is gated. WebCodecs in workers and VideoFrame transfer work on Safari 16.4 and later.

Browser client compliance

The client owns the entire RDP state machine: the gateway hands it the post-CredSSP plaintext stream and relays bytes in both directions. Compliance therefore lives almost entirely in protocol.js, rdpgfx.js and the codec files.

Legacy fast-path, input, display, channels

Legacy (non-GFX) rendering

  • Bitmap updates at 16 bpp only via WASM RLE; no bitmap cache; palette updates unsupported.
  • Pointer COLOR/NEW/CACHED handled; NULL, DEFAULT, POSITION and LARGE ignored although LARGE_POINTER is advertised (protocol.js:981-983).
  • Surface commands are dropped (client.js:1265) while SURFACE_COMMANDS, RemoteFX and FRAME_ACK capabilities are advertised and no TS_FRAME_ACKNOWLEDGE is ever sent. Advertise only what is rendered.
  • Drawing orders are correctly declined.

Input

  • 89-entry e.code scancode map; arrows are numpad codes without EXTENDED; PrintScreen wrong; many keys missing and swallowed by preventDefault.
  • No Unicode input events despite advertising the capability; no dead keys or IME; no sync of Num/Caps/Scroll lock; no key-up flush on blur.
  • Mouse buttons 1-3 only; buttons 4 and 5 release as MOVE; wheel encoding is correct per 2.2.8.1.1.3.1.1.3; no pointer lock, touch or pen.
  • Keyboard layout detection is sound.

Display

  • Dynamic resize via DISPLAYCONTROL works for a single monitor; HiDPI via desktopScaleFactor; fullscreen button present.
  • No multi-monitor; RESET_GRAPHICS monitor list ignored.

Channels

  • Clipboard: long format names only; CF_UNICODETEXT with a CF_TEXT fallback; no images, HTML, RTF, files or locking; 1600-byte chunking correct.
  • Audio out: PCM 44.1/22.05 kHz only, no jitter buffer; mic via deprecated ScriptProcessorNode; camera NV12 only via getImageData on a timer.
  • DVC: capability version negotiation, v3 compression, DATA_FIRST reassembly and 1600-byte fragmentation are correct; the drdynvc handler assumes single-chunk static channel PDUs (protocol.js:2212-2214).
  • MS-RDPEVOR and MS-RDPEGT are rejected or dropped, which is acceptable.

Resilience

Auto-reconnect, redirection handling and the ordered-decode barrier are well built. Holes: a worker onerror never settles pending requests, which can wedge the barrier (rdpgfx.js:176-179); an unsupported H.264 configuration is silent; and requestKeyframe is undefined at its two call sites.

Gateway protocol code

Design is sound: RdpRelaySession does TCP, X.224, TLS and CredSSP toward the host, then pumps opaque bytes through a bounded channel to the browser. The large decode engine in RdpSession, RdpChannels and friends exists only for recording and diagnostics, so its bugs cannot corrupt a live session. The native-client MITM path (MitmRdpStream, CredSspServer) is never instantiated.

What is correct

  • X.224 Connection Request and Confirm framing, HYBRID and SSL requested, standard RDP security refused, HYBRID_EX early user authorisation consumed and re-synthesised.
  • CredSSP TSRequest v6 encoding, client nonce and hash, TSCredentials sealing, NTLMv2 with MIC and timestamp echo, TLS 1.2/1.3 with SNI.
  • MPPC and ZGFX ports match the specification for well-formed input; DVC parsing including v3 compression; Server Redirection field order; routing token replay in the Connection Request.
  • Backpressure toward the host through a bounded channel; error paths close streams without socket leaks.

VDI broker & Proxmox

What exists

Dedicated pools with lazy clone-on-connect work end to end: template check, VMID from cluster/nextid, insert instance rows, clone, poll the task, stamp the ksol-rdpgw-id note, apply cloud-init identity with optionally generated per-user credentials stored as the owner's SSO row, then the normal start/guest-agent/IP/RDP-probe readiness. Every VM destroy goes through SafeDestroyInstanceVmAsync, which verifies the note before destroying; that invariant holds at both call sites.

What does not exist

Stubs that the UI and docs present as shipped

  • Floating pools return "not yet available" (VdiProvisioningService.cs:70-71); Leased and Returning states, MaxSize and FloatingResetMode have no consumers.
  • GuestAgent identity mode logs "not yet applied" (VdiProvisioningService.cs:302-303); the domain, OU, join user and join password fields are stored and never read.
  • HostnamePattern is stored and never applied; the clone's hostname is the sanitised VM name.
  • Kerberos realm and KDC on the backend are consumed by the relay but absent from the bind lists and views, so they can only be set by editing the database.
  • No reconcile loop of any kind; "reconcile" appears only in comments.

Lifecycle holes

  • Stuck-in-Provisioning after a restart is unrecoverable: the next connect inserts a second row and hits the unique (pool, owner) index, and the dashboard keeps showing the clone card (VdiProvisioningService.cs:74-104, 385-402).
  • Clones are excluded from the idle reaper and the status service (IdleReaperService.cs:82, 127; ResourceStatusService.cs:100).
  • Clone timeout marks the instance Failed while the Proxmox task continues; the VM is later abandoned unstamped and adopted by discovery as a plain resource.
  • The notes-stamp return value is ignored (VdiProvisioningService.cs:184); an unstamped Ready clone can never be safely destroyed.
  • No concurrency limit on clones, no VMID reservation, no retries at any layer, no name-collision handling.
  • Deprovision and pool delete do not check for a live session; the VM is hard-stopped under the user.

Connectors, Proxmox client, sessions, data model

  • Connectors carry ciphertext only (TLS and CredSSP are layered on top of the tunnel), which is the right design. But AllowScope is enforced only during the RTT race, the agent dials whatever host and port it is told, the token is accepted from the query string, there is no protocol version, and LastSeenUtc is written only at connect and close despite the 20-second pings.
  • Proxmox client creates a new HttpClient and handler per call, collapses every failure to null or false so 403 and 500 look identical to users, defaults VerifyTls to false, and has a single host per backend with no alternate endpoints.
  • Sessions live in memory, do not survive restarts, and every WebSocket is a new record; a reconnect briefly counts twice, so a per-user cap of one can reject the user's own reconnect.
  • Data model: RDPResource.VdiInstanceId has no foreign key; no unique index on (backend, VMID); the assignment XOR is enforced only in the controller; no concurrency tokens while the status service rewrites PowerState every 15 s; deleting a backend that owns pools throws an unhandled exception (ProxmoxBackendsController.cs:121-130).
  • Manual resources: Wake-on-LAN uses only the limited broadcast; SSH shutdown has no host-key verification or timeout; the Windows shutdown passes the password on the command line (ResourceShutdownService.cs:103-104).

Security & operations

What is good

  • Keyring sealed with PBKDF2-HMAC-SHA256 at 200k iterations and AES-256-GCM with a random nonce per blob; production refuses to start without the passphrase; a git-tracked-keyring guard exists.
  • All VM, IPMI, SSH, Windows, cloud-init and Proxmox secrets are encrypted at rest; stored credentials never reach the browser (confirmed in HomeController, Console.cshtml and the relay).
  • Registration is closed; connector tokens are 256-bit random, hashed, constant-time compared and single-use; recordings are Admin/Auditor only; ResourceAccessService is used at every connect path.
  • Rate limiting, lockout and MFA enforcement exist; recordings are encrypted with per-file nonces and carry per-track hashes.

Operations

There is no health endpoint, no metrics, no structured log sink, no backup procedure, no version display, no drain on shutdown and no rollback path. Everything that keeps the system consistent (sessions, readiness jobs, redirection tokens, connector state, policy caches, rate-limit partitions, DataProtection keys, the SQLite file) is process-local, so the product is a single instance by construction. That is acceptable for a first release if it is documented as such and the state is at least persisted across restarts; today a restart also forgets every live session and every in-flight provision.

Admin UI & processes

What is already well done

  • One design system throughout: shared list toolbar, pagination, confirm modal replacing native dialogs, toasts from TempData, tab memory across POST-redirects, and a picker partial reused for every grant.
  • Access provenance is explicit: every access row shows Direct or via-Group with a link to the group, and group-derived access can only be revoked on the group. Managing a grant from both the user page and the resource page behaves identically.
  • Secrets are handled correctly in forms: "leave blank to keep", never rendered back, placeholders show that a value exists.
  • Safe destructive flows: pool delete verifies every VM's identity before destroying and aborts cleanly if the backend is unreachable; Proxmox resource delete explains re-discovery.
  • Connector enrolment shows the one-time token with copy buttons and the exact command.
  • The resource editor shows Proxmox RRD sparklines for CPU, memory, network and disk.

Where it falls short of a professional console

Dashboard is a count board, not an operations view

Views/Admin/Index.cshtml shows seven totals, five recently active resources, four quick links and backend online status polled every 30 s. Nothing tells an operator what needs attention: no connector status, no stuck or failed provisions, no pool capacity or spare count, no recent failed logins or audit failures, no keyring or SMTP health, no version. The "Access grants" tile links to a read-only overview page.

Onboarding has no path

From an empty install to a user on a pooled desktop takes roughly eight page hops with no guidance: add a backend (no "test connection", TLS verification unchecked by default, Discover runs synchronously in the request), create a pool (six fields on Create, then a 250-line single-form Manage page that mixes configuration, assignments and instances), add a user (no invite e-mail, no "must change password", no password policy shown), assign, and connect. Nothing validates the template up front (cloud-init drive, guest agent, target storage), so a misconfigured pool is discovered by the first user at connect time as "Failed to start cloning".

User lifecycle is missing

Controllers/UsersController.cs offers create, rename e-mail, delete, roles, groups, grants and pools. There is no reset password, unlock, disable or enable, force MFA re-enrolment, invite, or session list. The users list loads every user in one query with no pagination and no filter by status or MFA. Roles are a raw checkbox list of Admin, Auditor and User.

Pools

  • Update has no validation: VMID range order, port, max size, template, Linked mode with a target storage are all unchecked (VdiPoolsController.cs:141-153).
  • The instance table shows VMID, owner, state and creation time; not power state, IP, template version, last session or any action other than Deprovision. No start, stop, re-provision, re-image or maintenance.
  • Kind "Floating" is selectable and documented but returns an error at connect. TempData is rendered inline on this page as well as through the toast host, so messages appear twice.

Backends and connectors

  • No test-connection action; Kerberos fields not exposed; deleting a backend that owns a pool throws.
  • Connector "Last seen" reflects connect and disconnect only; no agent version; no per-connector metrics.

Sessions, audit, recordings

  • Sessions: user, resource, host, IP, start and duration; then a full page reload every 15 s. No codec, bandwidth, latency or client; no logoff as distinct from disconnect; no message to user; no shadowing.
  • Audit: category and text filter only; no date range, no actor filter, no export, detail truncated to a tooltip, no retention or integrity indicator.
  • Recordings: good synchronised four-track player with integrity verify; no filters beyond text, no download, no bulk delete, playback not audited.
  • Recording rules: the Target column prints raw user and resource GUIDs (Views/RecordingRules/Index.cshtml:775-777); the form shows all three scope selects regardless of the chosen scope.

Consistency

  • Three date conventions: UTC "u" on the dashboard and resource pages, local "g" on connectors and pools, UTC "yyyy-MM-dd HH:mm:ss" on sessions and audit. Pick one and show the zone.
  • English only; no unsaved-changes warning on the long forms; no optimistic concurrency, so two admins editing the same resource silently overwrite each other.
  • Device policy covers four features; drives, printers, USB and smart cards are absent because the client has no RDPDR, but the page does not say so.

End-user experience

What works

  • A clear launcher with power badges and a Pool badge; per-card connection settings and stored credentials with clear wording about where they live.
  • A preflight stepper (checking, starting, guest agent, IP, RDP probe, finalising) with retry.
  • A distinct reconnecting overlay that keeps the last frame, counts down two minutes, retries every 15 s and offers retry-now and cancel; a separate SSO reconnect card.
  • A connection-quality pill with per-leg latency on hover; a recording banner when a rule requires notice; a floating auto-hiding toolbar.

Where users get stuck

  • First pooled connect looks frozen. The readiness service reports a provisioning phase (ConnectionReadiness.cs:10) but the console's step list omits it (Console.cshtml:1037-1046), so pfRender returns early and the bar stays at "Checking resource… Step 1 of 6" for the whole clone. No ETA, no cancel.
  • Keys do not work as expected. Arrow keys reach the host as numpad keys, so with Num Lock on they type digits; Home, End, Page Up/Down, Insert and Delete are not mapped at all; AltGr and the Win key are missing, so the documented "your layout is detected automatically" is only partly true.
  • Thin toolbar. Clipboard, fullscreen, mute, camera, microphone and disconnect. No Ctrl+Alt+Del, no keyboard layout switch, no settings during a session, no fit/1:1 scaling toggle, no session timer, no logoff as distinct from disconnect, no detailed stats.
  • Clipboard is text only and manual. The panel design is reasonable given browser constraints, but there are no images, HTML or files.
  • No touch or pen. There are no touch handlers, so iPad and phone users cannot operate the desktop.
  • Generic failures. Every Proxmox or NLA failure reads as "contact an administrator" or "bad credentials or NLA refused"; locked, expired and disabled accounts are indistinguishable.
  • Silent black screen when the browser cannot decode H.264 (see Safari section).
  • Launcher lacks search, favourites, recency and an "in use elsewhere" indicator; Connect opens a new tab, which pop-up blockers interrupt (the troubleshooting doc already has to explain this).
  • Account self-service is the stock Identity scaffold: no "sign out everywhere", no active session list.

Method

Four focused code audits (gateway protocol, browser client with a Safari lens, broker and infrastructure, security and operations) read the source against the six Microsoft protocol specifications in the repository, and a fifth pass read every admin and user controller, view, shared partial and documentation page for process and UX. The highest-impact claims were re-verified by direct inspection before publication. Nothing was executed, and the repository was not modified. Line numbers refer to commit 68add31; paths are relative to KSol.ZeroVDI/ or wwwroot/lib/rdpweb/ as context makes clear.

Comparison points used for "professional grade": Windows App web client, Citrix Workspace HTML5 and Studio/Director, Omnissa Horizon HTML Access and Console, Azure Virtual Desktop host pools, Kasm Workspaces, Apache Guacamole, Teleport.
