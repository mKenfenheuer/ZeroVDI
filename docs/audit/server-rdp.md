# ZeroVDI server-side RDP audit (KSol.ZeroVDI/RDP + Controllers)

Paths relative to `/Users/max/Git/ksol-rdpgw/KSol.ZeroVDI/`. Read-only; every claim cites file:line.

## 1. Relay design

**Browser path.** `Controllers/RdpWebSocketController.cs:74-293` accepts the WS, authorizes, resolves the host and hands the socket to `RDP/RdpRelaySession.cs`. The relay does only: optional first-frame JSON creds (`RdpRelaySession.cs:228-247`); TCP + X.224 negotiation + TLS-client + CredSSP-client via `RdpHostConnection.ConnectAsync` (`RdpHostConnection.cs:85-194`); a `{status:"ready", selectedProtocol}` frame (`RdpRelaySession.cs:155-156`); then two opaque pumps — host SSL → bounded Channel(256×16 KB) → WS binary (`:267-357`) and WS binary → SSL (`:359-388`). The comment at `:11-17` is accurate: "the browser JS owns all MCS/PDU/fastpath/bitmap/input logic". The gateway is a **TLS/NLA-terminating MITM that hands the post-CredSSP, pre-MCS-Connect-Initial plaintext stream to the browser**, not a decoding client.

**Native mstsc path (RDGW).** `RDP/MitmRdpStream.cs:147-229`: X.224 *server* (`:235-283`), TLS server with the gateway cert (`:160-167`), `CredSspServer` validating the client's NTLMv2 against the gateway-login NT hash (`:172-179`), then `NlaRdpResolver` opens the host with stored SSO creds (or the delegated ones) and relays plaintext (`:323-355`). Client-requested protocols are passed through so SC_CORE `serverSelectedProtocol` matches (`:203-211`).

**Capabilities.** Built entirely by the browser; there is no C# code emitting MCS Connect Initial, Client Info, Confirm Active or any capset — those names appear only in the passive decoders. `RdpSession.cs`/`RdpX224.cs`/`RdpChannels.cs`/`RdpShare.cs`/`RdpFastPath.cs` form a **round-trip decode/re-encode engine for diagnostics and recording** (`RdpSession.cs:1-9`, `Feed :100-147`): its output is consumed only by `RdpStreamRecorder` (`RdpStreamRecorder.cs:88`) and never substituted into the live stream, so decoder bugs cannot corrupt a session — they only break recordings. The only protocol-level value the gateway forces is `HYBRID|SSL` toward the host (`RdpRelaySession.cs:133`), echoed back so the browser stamps the right `serverSelectedProtocol` (`:152-156`). HYBRID_EX Early User Authorization Result is consumed on the host leg (`RdpHostConnection.cs:179-189`) and re-synthesised toward the native client (`MitmRdpStream.cs:184-189`) — correct per [MS-RDPBCGR] 2.2.10.2.

**Framing.** WS message boundaries carry no meaning: partial WS frames are written straight to the host (`RdpRelaySession.cs:378-383`) and host slices are whatever `SslStream.ReadAsync` returned (`:298-302`). Text frames are intercepted as ping/pong (`:370-376`), so they cannot leak into the RDP stream.

## 2. Connection sequence — what C# actually does

Only 1.3.1.1 step 1 (X.224) plus TLS + CredSSP (5.4). Everything from MCS Connect Initial to Persistent Key List is browser-generated and relayed opaquely; items 2(b)–(k) of the brief are not auditable server-side (see `wwwroot/lib/rdpweb/protocol.js`).

**X.224 host leg — `RdpHostConnection.cs:200-256`.** CR = fixed 7 bytes + optional routingToken + RDP_NEG_REQ (`:222-226`), order per 2.2.1.1 (`Spec/[MS-RDPBCGR].md:1587-1614`). `requestedProtocols` default `HYBRID|SSL` (`:86`); RDSTLS never requested (fine — servers only pick it if offered). RDP_NEG_REQ `flags` always 0 (`:205`); in the MITM path the client's flags/rdpCorrelationInfo are dropped (`MitmRdpStream.cs:248-252`). CC parse `:242-255` reads type @7 and selectedProtocol/failureCode @11 (correct for LI=14). A CC without rdpNegData → "server did not select TLS/NLA" (`:255`): **standard RDP security (RC4) is refused** — right posture. **NEG_RSP `flags` (byte 8) is discarded**: EXTENDED_CLIENT_DATA_SUPPORTED / DYNVC_GFX_PROTOCOL_SUPPORTED / RESTRICTED_ADMIN_MODE_SUPPORTED never reach the browser (only `selectedProtocol` does, `RdpRelaySession.cs:155-156`), so the browser cannot gate CS_MONITOR/CS_MCS_MSGCHANNEL on it per 3.2.5.3.2. NEG_FAILURE `failureCode` is logged and collapsed into "RDP negotiation failed" (`:249-250`); `NlaRdpResolver.cs:31-41` then retries TLS-only whenever HYBRID was requested — also for HYBRID_REQUIRED_BY_SERVER(5)/SSL_WITH_USER_AUTH_REQUIRED_BY_SERVER(6), where the retry is futile and costs another 10 s attempt (`NlaRdpResolver.cs:23,52-53`). That 10 s budget covers TCP+X.224+TLS+CredSSP together; a slow AD host is misreported as "negotiation failed" and retried TLS-only.

**X.224 MITM server side — `MitmRdpStream.cs:235-283`.** CC built correctly; HYBRID_EX selected only if offered (`:261`). **Bug (High):** `ExtractRoutingToken` returns null for the standard `Cookie: mstshash=<user>\r\n` (`:311` — "mstshash=" does not contain "msts="), so `negOff` stays 7 (`:250`), `crBody[7]` is 'C' not `TYPE_RDP_NEG_REQ`, and `requested` remains 0 (`:248-252`). The host leg is then opened with `requestedProtocols=0` = PROTOCOL_RDP (`:208-211`); an NLA-required host answers NEG_FAILURE, a permissive one selects standard security and the gateway still attempts TLS (`RdpHostConnection.cs:127-140`) — either way the connect fails, and `NlaRdpResolver` will not retry because HYBRID is not in the requested set (`NlaRdpResolver.cs:34`). mstsc sends the mstshash cookie whenever a username is pre-filled. Fix: skip *any* CRLF-terminated token before looking for RDP_NEG_REQ (2.2.1.1: cookie and routingToken are mutually exclusive), forward it only when it is `msts=`.

## 3. Post-connection behaviours

Auto-reconnect/ARC, Deactivate/Reactivate, Heartbeat, Auto-Detect, Multitransport, Save Session Info, Set Error Info, Monitor Layout, Shutdown Denied, Refresh Rect/Suppress Output and Frame Marker are all browser concerns; no C# touches them on the live path (`RdpShare.cs` labels a few for logs, section 6). Consequences: **Set Error Info is never mapped** — a host disconnect after ERRINFO_* surfaces only as "remote desktop disconnected" (`RdpRelaySession.cs:215-219`) although the 64 KB redirect scan tail (`:287`) already holds the last PDUs; nothing server-side retains the ARC cookie, so every browser reconnect is a fresh TCP/TLS/NLA session.

**Server Redirection (2.2.13) — `RdpServerRedirection.cs`, `RdpRelaySession.cs:279-337`, `RdpWebSocketController.cs:141-147,225-231`.** The scan anchors on TPKT + X.224 Data + MCS SDin then searches ≤40 bytes for `SEC_REDIRECTION_PKT` (`RdpServerRedirection.cs:82-104`), tries RedirFlags at +8 (Enhanced form 2.2.13.3.1) and +12 (Standard form with basic security header 2.2.13.2.1) (`:120`); field order TargetNetAddress→LoadBalanceInfo→UserName→Domain→Password→TargetFQDN matches `[MS-RDPBCGR].md:9127-9144`. Routing token is re-sent in the X.224 CR (`RdpHostConnection.cs:209-226`) — correct. **Gaps:** `TargetHost` is parsed but **never used** — the callback stores only token + creds (`RdpWebSocketController.cs:228-230`) and the reconnect uses the original `_host` (`RdpRelaySession.cs:130-135`); a redirect *without* LoadBalanceInfo is not acted on at all (`:314`) and is forwarded to the browser. RD Connection Broker redirects rely on TargetNetAddress/FQDN, so Windows RDS farms break. `LB_NOREDIRECT` ignored; TargetNetBiosName/TsvUrl/RedirectionGuid/TargetCertificate unparsed (harmless). `LB_PASSWORD_IS_PK_ENCRYPTED` passwords are dropped unless printable (`:181-190`) — right for GNOME RD, but Windows brokers expect the opaque cookie echoed back as the password. Redirect state lives 30 s keyed by (user, resource) (`RedirectionTokenCache.cs:26`) — a second tab can consume it. The handover heuristic re-arms on *any* host close of a token-bearing leg with no retry cap (`RdpRelaySession.cs:198-209`).

## 4. Security

**TLS.** Host leg accepts *any* certificate (`RdpHostConnection.cs:127-132`), TLS 1.2/1.3 (`:138-139`), SNI = configured host (`:137`); no pinning/TOFU/fingerprint exposure. The comment "CredSSP's public-key binding still detects MITM" is wrong for the host leg (below) and void on the TLS-only fallback (`NlaRdpResolver.cs:40`), where the user types credentials into an in-band login over an unauthenticated TLS session. Client leg (MITM): TLS 1.2/1.3 with the gateway cert (`MitmRdpStream.cs:160-167`).

**CredSSP client (`CredSspClient.cs`).** TSRequest DER v6 (`:37,155`), tags [1]/[2]/[3]/[5] correct, errorCode [4] parsed as unsigned NTSTATUS (`:227-238`); server `version` read and ignored (`:196-198`), so a v2-4 server gets a nonce-hash it cannot verify (Low). pubKeyAuth = SHA256("CredSSP Client-To-Server Binding Hash\0"‖nonce‖SubjectPublicKey) sealed at seq 0 (`:99-105`), 32-byte CSPRNG nonce, key bytes = `PublicKey.EncodedKeyValue.RawData` (`RdpHostConnection.cs:165`) — correct. **Bug (High):** the server's pubKeyAuth is never unsealed or compared (`:114-119` checks `!= null` only; `ServerSealing`/`ServerSigningKey` at `NtlmClient.cs:58-60` are never used). [MS-CSSP] 3.1.5 step 5 requires verifying the Server-To-Client hash before sending TSCredentials. Combined with accept-all TLS, an active MITM can complete the handshake by returning *any* pubKeyAuth; it cannot unseal TSCredentials, but it fully observes the RDP session. TSCredentials encoding (`:307-334`), seq numbers 0/1 (`NtlmClient.cs:391`) correct (comment "seq 2" at `:121` is stale). Non-zero `errorCode` → one generic message (`:116-117`): no mapping of STATUS_LOGON_FAILURE/ACCOUNT_LOCKED_OUT/PASSWORD_EXPIRED/ACCOUNT_DISABLED/PASSWORD_MUST_CHANGE. **Kerberos is dead code:** `AuthenticateAsync` calls only `AuthenticateNtlmAsync` (`:61-78`); `KerberosAuth.TryGetApReqAsync` has no caller (grep: definition only), and `KerberosAuth.cs:58-62` yields an AP-REQ without the GSS wrap needed for pubKeyAuth/TSCredentials. Hosts with NTLM restricted are unreachable. Raw NTLMSSP in negoTokens (no SPNEGO) is accepted by Windows and FreeRDP-based hosts.

**NTLMv2 (`NtlmClient.cs`).** NTOWFv2, temp blob, NTProofStr, SessionBaseKey, KEY_EXCH (`:118-169`), sign/seal key magic (`:353-365`), ESS seal-then-checksum with a shared RC4 handle (`:386-409`) — per [MS-NLMP] 3.3.2/3.4.4.2/3.4.5. MIC with MsvAvFlags 0x02 (`:227-244,185-188`) and MsvAvTimestamp echo (`:135-137`) correct. **Gaps:** MsvAvChannelBindings is always 16 zero bytes (`:231`) — Windows sends MD5(gss_channel_bindings{tls-server-end-point:<cert hash>}); EPA-enforcing hosts reject. AUTHENTICATE echoes the client's flags without intersecting the CHALLENGE (`:329`, `serverFlags` unused) — 3.1.5.1.2 requires the negotiated set. Type 1 sets OEM_WORKSTATION_SUPPLIED with no workstation (`:47-50,85-88`). SPN is `TERMSRV/<host as configured>` (`CredSspClient.cs:82`) — IP-based when the resource is an IP; Windows tolerates it.

**CredSSP server (`CredSspServer.cs`).** Purpose: let native mstsc authenticate to the gateway with the user's *gateway* password while the host is opened with stored SSO creds, so the user never learns the host password. Version `min(client,6)` (`:79`); v5+ nonce path and v2-4 pubKey+1 path (`:119-139`) per [MS-CSSP] 3.1.5; client pubKeyAuth checked with `FixedTimeEquals` (`:127`); TSCredentials decoded (`:323-343`, credType 1 only — smart-card/remote-guard throw and become "handshake failed"). **Gaps:** AUTHENTICATE MIC never verified and MsvAvTargetName/ChannelBindings not inspected (`:93-104`, `Ntlm.cs:138-206`) — [MS-NLMP] 3.2.5.1.2 requires the MIC check when 0x02 is set (indirectly covered by the sealed pubKeyAuth); the claimed username is not compared with the expected identity (`:99` — acceptable since the caller picks the hash, but audit logs show the client-claimed name); no TSRequest with `errorCode` is sent on failure, so mstsc shows a generic error.

## 5. Virtual channels & DVC (recorder/diagnostics only)

CS_NET names (`RdpX224.cs:264-281`) are mapped positionally to SC_NET ids (`:287-299`, `RdpSession.RebuildChannelMap :216-223`) — correct per 2.2.1.4.4. `SkipChannelJoin` is recorded (`RdpX224.cs:285`) but unused.

- **CHANNEL_PDU_HEADER** (`RdpSession.ReassembleSvc :245-273`): FIRST/LAST handled; `totalLen` and the 1600/VCChunkSize limit are never validated. MPPC per chunk before reassembly is right (history spans chunks). **Bug:** the comment at `:44-46` says MPPC contexts are keyed "name|dir" but `:255` keys `name|level`, and `_svcReasm` (`:267-272`) is keyed by name — both directions share state, so interleaved c2s/s2c multi-chunk cliprdr/rdpdr messages corrupt each other (real on the MITM path where mstsc compresses c2s data).
- **DVC (MS-RDPEDYC)** (`RdpChannels.cs:218-328`): cmd/sp/cbId, CAPABILITIES pad+version (`:249-256`), CREATE (`:258-280`), DATA_FIRST Length width from `sp` (`:297`, 2.2.3.1), v3 compressed data through a per-channel ZGFX context (`:305-312`) — matches 3.1.5.1.4 (`[MS-RDPEDYC].md:1365`). Soft-Sync recognised, not parsed (`:320-323`).
- **Bug (High for recordings):** `RdpSession.ReassembleDvc :276-292` keys the DATA_FIRST accumulator by channel id only while both directions feed one session in wire order (`RdpStreamRecorder.cs:83-88`). The browser answers every END_FRAME with FRAME_ACK + QOE_ACK as `DVC_CMD_DATA` on the *same* Graphics channel id (`wwwroot/lib/rdpweb/rdpgfx.js:748-790`, `protocol.js:2013`). When an ack lands while a multi-chunk server frame is pending, `:284-287` appends it into the server's accumulator, completes it early with garbage inside, and the remaining server chunks are returned as stand-alone DATA (`:291`) — exactly the "non-ZGFX GFX-channel DATA (raw continuation)" the code works around at `RdpChannels.cs:495-518`. The same sharing affects `_dvcZgfx`/`_gfxZgfx`: the browser's acks are ZGFX `0xE0` raw segments (`rdpgfx.js:117-118`) and `DecodeGfx :503-510` runs them through the **server-direction** context, whose `HistoryWrite` (`Zgfx.cs:126-135`) pollutes the 2.5 MB history. GNOME RD (FreeRDP emits raw segments only) is unaffected; Windows RDS uses cross-PDU matches and will produce corrupted GFX headers → dropped/garbled recorded frames. Fix: key all three maps by (dir, id) and never feed c2s payloads into the s2c ZGFX.
- **Recognised DVCs** (`DispatchDvcPayload :331-372`): Graphics (full RDPGFX decode `:489-629`, AVC420/444 extraction `:637-686`, progressive via `GfxProgressiveCompositor`/`RfxProgressiveDecoder`), DisplayControl (`:467-484`), AUDIO_PLAYBACK_DVC (`:339-346`), AUDIO_INPUT (`:378-430`), Video/Geometry logged only (`:357-358`), RDPECAM via the enumerator heuristic (`:364-367,435-456`). Telemetry/ECHO/rdpinput/Location are opaque — fine for a recorder. AVC444 LC/cb1 split (`:648-662`) matches 2.2.4.5; WIRE_TO_SURFACE_2 4-byte bitmapDataLength handled (`:600-603`).

## 7. Compression

- **MPPC** (`Mppc.cs`): FreeRDP port; 8K/64K tables (`:117-150`), FLUSHED clears + AT_FRONT resets (`:100-101`, order irrelevant since both zero the offset), uncompressed packets bypass history (`:102`, matches 3.1.8.2.2 flush-on-expansion). 8K level uses a 64 KB buffer with a 0x1FFF source mask but unmasked writes (`:152-153`) — wrong only for a non-conformant compressor. **No bounds check** on `hp`/`srcIdx` in the copy loop (`:153`): hostile input throws (caught per unit at `RdpSession.cs:117-123`) and desyncs the context. `RdpSession.cs:253-254` maps RDP6/6.1 types to 8K MPPC (wrong algorithm; unreachable because the browser advertises 8K only, `protocol.js:2067`).
- **ZGFX** (`Zgfx.cs`): FreeRDP port; SINGLE/MULTIPART (`:230-257`), 2,500,000-byte history (`:16`, `[MS-RDPEGFX].md:3296`), 65,536-byte segment cap (`:17`), token table per 3.1.9.1 (`:20-32`). **Robustness:** MULTIPART allocates `new byte[uncompressedSize]` straight from the wire (`:242`) — a hostile host forces a 4 GB allocation; cap at `segmentCount×65536`. Direction sharing: section 5.

## 8. Robustness (live relay)

- **Hostile-host bounds:** CC length < 4 → negative array → generic failure (`RdpHostConnection.cs:239-240`, OK). CredSSP DER accumulation is unbounded (`CredSspClient.cs:258-280`, `CredSspServer.cs:283-305`) — time-bounded by the 10 s attempt on the client side; the MITM server side has **no timeout at all** (`MitmRdpStream.cs:147-229`), so a connected-but-silent client pins a front-end task until the RDGW library disposes the stream. NTLM parsers throw on short input and are caught (`NtlmClient.cs:105-115`, `Ntlm.cs:143-174`).
- **Timeouts:** only the 10 s connect budget (`NlaRdpResolver.cs:23`). Host death is detected by TCP keepalive on direct TCP (`IHostTransport.cs:40-46`) but not on the connector transport. Final `SendStatusAsync`/`CloseAsync` use `CancellationToken.None` (`RdpRelaySession.cs:218,223`) — an unresponsive browser can pin the request.
- **Backpressure:** host→browser bounded channel with `FullMode.Wait` (`:270-276`) — a slow browser stalls the host after ~4 MB instead of OOM (sound). MITM channels are unbounded (`MitmRdpStream.cs:47-50`). The recorder queue is unbounded (`RdpStreamRecorder.cs:47`) while its consumer does full RFX-progressive decode + BGRA composite per frame — no drop policy, so CPU-bound recordings accumulate.
- **Cancellation:** cancelling `ReceiveAsync` aborts the WebSocket (`:172-173`), so an admin force-disconnect (`RdpWebSocketController.cs:252-253`) looks like a network drop and the browser's auto-reconnect defeats it unless the tracker refuses the next connect. Reader exceptions are logged but only propagate via channel completion (`:342-344`). Error paths dispose only `netStream` (`RdpHostConnection.cs:114,145,160,171,186`) — no socket leak.
- **Thread safety:** `_redirected` (`:316,:174`) relies on await barriers; `RdpSession` is single-consumer (`RdpStreamRecorder.cs:13-16,47-49`); `RedirectionTokenCache` is concurrent with TTL cleanup only on consume.
- **Side effects:** `SampleHostRttAsync` opens and closes a raw TCP connection to the RDP port every 15 s for the session lifetime (`RdpRelaySession.cs:395-409`, `IHostTransport.cs:58-71`) — xrdp logs each, Windows counts them, IDS/fail2ban rules trip.
- **Credentials:** held as strings; `Rc4` never disposed by `NtlmClient`; redirect one-time passwords in memory ≤30 s. `ReadCredentialsAsync` has no size cap/timeout (`:228-247`). Acceptable.

## 10. Prioritised gap list

**Critical**
- C1 Verify the server pubKeyAuth in `CredSspClient` (bug 1) — the accept-all-cert policy rests on a MITM check that is not performed. All hosts.
- C2 Direction-key the recorder's DVC/SVC reassembly, MPPC and ZGFX contexts (bug 3) and fix `_rx` growth on framing errors (bug 4). Recordings from Windows RDS/Win10-11 are unreliable today and memory is unbounded.

**High**
- H1 MITM path: skip any CRLF token before RDP_NEG_REQ (bug 2). Breaks native mstsc with a pre-filled username.
- H2 Honour TargetNetAddress/TargetFQDN/LB_NOREDIRECT and redirects without LoadBalanceInfo; echo the PK-encrypted password on reconnect (bug 5). Windows RDS with RD Connection Broker.
- H3 Wire Kerberos (SPNEGO + GSS wrap) or remove the claim (bug 6); add `tls-server-end-point` channel binding (bug 8). Hardened AD / "Restrict NTLM" / Protected Users.
- H4 Host certificate policy: TOFU/pin per resource and expose the fingerprint; the TLS-only (xrdp) fallback has no protection at all.

**Medium**
- M1 Map CredSSP errorCode, HYBRID_EX result, NEG_FAILURE and (by sniffing the last TPKTs before EOF) ERRINFO_* to user-facing messages; stop the futile TLS retry (bugs 14, 15).
- M2 Relay RDP_NEG_RSP flags to the browser (bug 7). Old xrdp / non-Microsoft servers.
- M3 Recording fidelity: reassemble/inflate fast-path updates before `PointerTracker` (bug 10); cap ZGFX MULTIPART allocation (bug 11); bound the recorder queue with a drop policy.
- M4 SSL-only (xrdp) SSO: the gateway sees plaintext, so it could inject stored credentials into the Client Info PDU (INFO_AUTOLOGON); today SSO does nothing for xrdp hosts.
- M5 Admin force-disconnect should send a terminal status (or mark the session "kicked" in `SessionTracker`) before aborting, so the browser's auto-reconnect does not undo it.
- M6 Replace the 15 s throwaway TCP probe with something that does not hit the RDP listener, or make it opt-in.
- M7 Split the 10 s budget into separate TCP and NLA deadlines for slow domain hosts.

**Low**
- L1 NTLM flag negotiation (bug 9), OEM_WORKSTATION_SUPPLIED mismatch, LMv2 vs Z(24) with server timestamp, CredSspServer MIC/SPN/CBT checks and errorCode responses (bug 13).
- L2 Redirect cache consumable by a second tab; handover re-arm loop has no retry cap.
