## ★★★ ROOT CAUSE (2026-06-23, v6 — spec + Connect-Initial byte-diff): we never JOIN the MCS message channel
Decisive CS_CORE/GCC byte-diff (same C# decoder on BOTH our_c2s.bin and mstsc c2s.bin):
- mstsc GCC blocks: CS_CORE, CS_CLUSTER, CS_SECURITY, CS_NET. earlyCapabilityFlags=0x7af.
- OURS: same FOUR **plus CS_MCS_MSGCHANNEL (0xC006) and CS_MULTITRANSPORT (0xC00A)** — mstsc sends NEITHER.
Because we advertise CS_MCS_MSGCHANNEL, the host GRANTS a message channel: SC_MCS_MSGCHANNEL (0x0C04) body=ef03 → **MCS channel 1007**. But our client's `parseServerUserData` SKIPPED 0x0C04 (explicit `// SC_MSGCHANNEL ... skipped`) and our MCS join phase only joined 1008/1003/1004/1005/1006 — **never 1007**. Per [MS-RDPBCGR] 3.2.5.3.3 the client MUST join the granted message channel. We left it unjoined; the host's connection sequence can't run **network auto-detect** (we set RNS_UD_CS_SUPPORT_NETCHAR_AUTODETECT 0x0080 in earlyCapabilityFlags 0x7af, which runs over the message channel per 2.2.1.3.7) so it CLAMPS GFX bandwidth to ~nothing after the first few keyframe bursts. Exactly the symptom: 3 frames then throttle, host alive, no close.
This is why caps/acks/codec/SUSPEND/transport/MONITOR_LAYOUT all matched mstsc yet only WE got throttled — the divergence was in the Connect Initial (extra blocks → granted-but-unjoined message channel), not the GFX channel.
FIX CHOSEN = B (match mstsc): STOP sending CS_MCS_MSGCHANNEL + CS_MULTITRANSPORT in clientUserData (protocol.js). The old comment claiming "omitting them → TCP drop" is FALSE vs this host (mstsc omits both and streams fine); the prior drop was some other framing bug. The two builder fns are kept but unreferenced. Also kept (inert): SC_MSGCHANNEL (0x0C04) parse → msgChannelId + guarded `if(this.msgChannelId) joinQueue.push` — a no-op when the host grants no message channel, correct if one ever does.
WHY NOT A (keep blocks + join 1007): tested live — joining 1007 made the host progress FURTHER but then it sent **Demand Active (reactivate) → DEACTIVATE_ALL** (session renegotiation), and our client mishandles reactivation (`fastpath: DROP 5B output update in state capabilities`). Ground truth: **mstsc gets exactly ONE Demand Active and ZERO Deactivate-All** — the working session never reactivates. So A pushes the host off mstsc's path; B keeps us on it.
KEEP: FRAME_ACK queueDepth=0 every frame (v5, matches mstsc). NEXT: test B — host should follow mstsc's single-DemandActive path and stream continuously. If B ALSO triggers a DEACTIVATE_ALL, the next fix is handling clean reactivation (re-send ConfirmActive on the new shareId).

## (likely SECONDARY, see v6) v5 — VERIFIED vs mstsc capture: SUSPEND was BACKWARDS
The SUSPEND "fix" (v3) was the BUG. Settled by analyzing the working mstsc MITM capture (/tmp/rdpmitm, 3.6MB s2c, meta.txt true order) against THIS host:
- mstsc sends a real **FRAME_ACKNOWLEDGE (cmdId 0x0d) with queueDepth=0 for EVERY frame** — 45 frame-acks, almost all queueDepth=0x0 (a few real buffered counts 0x55/0x15E/0x1778) — PLUS a QOE ack per frame (207 QOE total).
- mstsc sends **SUSPEND (0xFFFFFFFF) exactly ONCE, at the very END** (frame ~45, teardown). NEVER up front.
- The host's GFX scheduler is DRIVEN by this per-frame FRAME_ACK feedback loop: stream burst → wait for ack → stream more. mstsc's c2s shows relentless `C2S 44` (=20B FRAME_ACK) interleaved with the host's 10-29KB s2c bursts, all the way to 3.6MB.
Our browser did the OPPOSITE: sent SUSPEND on the FIRST END_FRAME then stopped FRAME_ACKs (QOE only). With no per-frame queueDepth signal this host throttles GFX to nothing and stops at frame 2-4 — deterministically. Spec §3.2.5.13 says SUSPEND means the server "MUST NOT block," but "not block" ≠ "keep streaming": this host needs the ack loop to schedule.
This explains EVERY prior symptom: deterministic stop at frame 2-4, host alive (other DVCs/Geometry keep flowing), no close, NODECODE still stalls (decoder irrelevant — it's the ack we send, not what we render). The "11184-byte mid-frame boundary" was just where the host had streamed one frame's worth and then waited for the next ack that never carried a queueDepth.
FIX: rdpgfx.js `_onEndFrame` — send FRAME_ACK queueDepth=0 EVERY frame + QOE every frame (mirror mstsc). `window.RDP_GFX_SUSPEND=1` forces the old up-front-SUSPEND for A/B only. (The pump split + off-hot-path recorder in RdpRelaySession.cs from the v4 transport theory are KEPT — they're harmless hygiene, decoupling browser WS speed from host pacing — but transport back-pressure was NOT the gate.)
NEXT: test — host should now stream past frame 3 and keep going (real video). If it does, this is the gate.

## BREAKTHROUGH (2026-06-23, v3): SUSPEND fix lets frames flow + real content
After the SUSPEND queueDepth fix, the stream now reaches frame 6-7 (was 3) and **real pixels decode** (frame 5: nonBlack=202/4111360, max=rgb(251,251,251), first@2466,1556 — a cursor/UI element). So the Unacknowledged-Frames block WAS a real gate and SUSPEND cleared it. BUT the stall now persists INTERMITTENTLY (2/4/6 frames, varies per run) — a timing/back-pressure race, not a hard protocol gate.
Two remaining hot-path throttles identified:
1. **Gateway recorder was synchronous on the s2c relay path** — RdpSession.Feed (full structural decode) ran under a lock per chunk in PumpSslToWsAsync, back-pressuring the host. FIXED: recorder now enqueues (Channel) and decodes on a background task; Feed() is copy+enqueue only.
2. **Browser WebCodecs decode queue grows** (queue=1→4) — AVC444v2 at 2560x1606 decodes slower than frames arrive; the WS send to the browser can then block, stop the gateway's host SSL read, fill the host TCP window, and pause the host. Likely the remaining intermittent stall. NEXT: test with recorder-off-hot-path; if still intermittent, decouple the gateway s2c pump from browser WS speed (bounded buffer) and/or reduce client decode load.
Render note: decoded frames still mostly all-black (nonBlack=0) except small UI rects — the genuine desktop is near-black; not a decode-color bug per se (copyTo BGRX path produces real pixels where content exists).

## (SUPERSEDED, WRONG — see v5) v3: host BLOCKS on Unacknowledged Frames; fix = SUSPEND queueDepth
This was the BUG, not the fix. SUSPEND on the first frame is the OPPOSITE of mstsc; the correct fix (v5) is FRAME_ACK queueDepth=0 every frame. Original (wrong) reasoning kept below for context.
Decisive: with NODECODE=1 (decoder fully bypassed, drop+ack only) the stall PERSISTS — so it's NOT the decoder. The host stops MID-MESSAGE at a deterministic boundary: last DataFirst declares totalLen≈22404 but only ~11184 bytes arrive (≈7 DVC chunks), every run. Server console shows NO close/error — the gateway's PumpSslToWsAsync is just blocked in ssl.ReadAsync; the HOST paused mid-frame without closing. So it's protocol-level flow control, not TLS/transport.
mstsc evidence: during a 110KB frame the host sends ~11 DVC chunks, then WAITS for a client FRAME_ACK/QOE, then continues (interleaved bursts). The host's GFX scheduler streams in bursts gated on the client draining its **Unacknowledged Frames** ADM ([MS-RDPEGFX] 3.2.1.2 / 3.2.5.13). With queueDepth=0 (QUEUE_DEPTH_UNAVAILABLE) the server has no buffering info and applies a conservative throttle that, on THIS Windows host, blocks after ~4 unacked frames.
Spec fix (3.2.5.13): queueDepth=SUSPEND_FRAME_ACKNOWLEDGEMENT (0xFFFFFFFF) → "server MUST clear the Unacknowledged Frames ADM and MUST NOT wait or block on unacknowledged frames." mstsc itself sends SUSPEND later in its session. FIX: rdpgfx.js `_onEndFrame` now sends one FRAME_ACK with queueDepth=0xFFFFFFFF on the first END_FRAME (then stops FRAME_ACKs; QOE acks continue). Toggle off via window.RDP_GFX_NO_SUSPEND=1. If this frees the stream, the Unacknowledged-Frames block was the gate — consistent with every prior elimination (caps/acks-structure/codec/camera/audio/Geometry/MONITOR_LAYOUT all correct but not the gate).
NOTE: earlier "tested queueDepth and it didn't help" almost certainly tested a real decodeQueueSize value (1..N), NOT the 0xFFFFFFFF SUSPEND sentinel — different spec semantics (throttle hint vs disable-blocking).

## ROOT CAUSE (2026-06-23, v2): client sends an unexpected DVC CLOSE on Geometry channels
Decisive evidence from true-order replay of our session: the host's s2c stops MID-MESSAGE — last GFX is a DataFirst declaring totalLen=22405 but only 11184 bytes arrive (11221 short). The host sends one big partial chunk then three tiny control PDUs (Create Geometry id=18, Create Geometry id=18, Close Geometry id=18) and goes dormant (last s2c t=828ms; session then idle 8s while we send only mouse moves).
Diff vs mstsc on the Geometry (MS-RDPEGT) channels: **mstsc NEVER closes Geometry — only the SERVER sends DVC CLOSE (all S2C Close), on its own schedule. Our client sent a CLIENT CLOSE (C2S Close) right after accepting each Geometry channel** ("accept-then-close"). The host then re-opened Geometry, we closed it again — a Create/Close war on the drdynvc static channel that coincides exactly with the GFX stall. The old code comment claiming "macOS app sends CLOSE" was WRONG (verified false against the fresh capture).
FIX: protocol.js `_dvcOnCreate` isGeometry branch — ACCEPT and KEEP OPEN (don't send a client CLOSE; the CREATE_RSP status 0 + dvcById registration already happened above). Let the host close it. Geometry DATA we receive falls to the unhandled-channel log (harmless; mstsc doesn't respond to it either).

A bare DVC DATA with no pending DATA_FIRST is a complete message. The "0x5d75d7 raw chunks" were a bug in a throwaway python script (misread DATA_FIRST 0x24 as DATA 0x34), NOT real.

## ROOT CAUSE (fixed)
The browser GFX stall (host streams ~3 frames then stops) was caused by **off-by-one capability-set TYPE numbers** in the client's Confirm Active PDU (`confirmActivePdu` in `protocol.js`). Per [MS-RDPBCGR]: LARGE_POINTER=0x1B, SURFACE_COMMANDS=0x1C, BITMAP_CODECS=0x1D, FRAME_ACKNOWLEDGE=0x1E ([MS-RDPRFX] 2.2.1.3). Our code sent them as 0x1C / 0x1D / 0x1E and **omitted FRAME_ACKNOWLEDGE entirely**. So the host read our LargePointer body as SurfaceCommands, SurfaceCommands as BitmapCodecs, BitmapCodecs as FrameAcknowledge — it never saw a valid SURFACE_COMMANDS cap (the GFX surface-pipeline gate) and mis-negotiated frame-ack, so it stopped streaming after the initial frames. Fix: correct the four types and add `capFrameAcknowledge()`; bodies are byte-for-byte what mstsc sends (LP `03 00`; SC `12 00 00 00 00 00 00 00`; BC the 23-byte GUID blob; FA `02 00 00 00`). Found by diffing mstsc's Confirm Active capsets (22 sets) against ours (15) via the MITM dump.

## Diagnostic trail (eliminations, kept for context)

The browser GFX H.264 stream stalls after ~3 logical frames (RESET + keyframe + 1 delta) against the test host ([[rdp-test-host]] 10.1.250.112). A MITM capture of a working mstsc/macOS-RDP session against the SAME host (tool at `/Users/max/Git/tools/rdpmitm`, dumps `/tmp/rdpmitm/{c2s,s2c}.bin` + `meta.txt`) streamed **3.3 MB s2c** vs our **~13 KB**. Comparing the two **eliminated** these as the cause:

- **DVC channel accept/reject is IDENTICAL to mstsc.** mstsc rejects CoreInput(id2), MouseCursor(id8), Video::Control(id10), Video::Data(id11); accepts Graphics(id7), Geometry(id12), audio. Exactly our decisions. So MS-RDPEVOR and MS-RDPEGT channel handling are NOT the gate (also confirmed by spec: EVOR is server-initiated and the host sent zero bytes on it; keeping Geometry open changed nothing).
- **GFX acks are IDENTICAL.** mstsc sends FRAME_ACKNOWLEDGE (0x0d, 20B) + QOE_FRAME_ACKNOWLEDGE (0x16, 20B) per frame — same PDUs/sizes as us.
- **The host needs NO client keep-alive.** During mstsc's keyframe burst and the next burst, mstsc's c2s stayed frozen (sent nothing) while the host kept streaming. So there is no magic post-keyframe PDU we're missing.
- **Decoder is NOT involved.** window.RDP_GFX_NODECODE=1 (drop+ack frames, no WebCodecs) still stalls at the same point.
- **Input is well-formed and ignored.** Keyboard (scancodes) + mouse moves all correctly framed per [MS-RDPBCGR] 2.2.8.1.2.2 and on the wire; host produces zero GFX in response.
- **Acks aren't malformed.** Per [MS-RDPEGFX] 3.2.5.13 the server only uses frameId + queueDepth (we send 0 = keep streaming); totalFramesDecoded is not used for flow control.

**Remaining suspect = the INITIAL capability negotiation.** Since our post-keyframe GFX c2s matches mstsc but the host throttles only us, the host likely classifies our client as not-sustained-video-capable from the MCS Connect Initial (CS_CORE earlyCapabilityFlags) or the Confirm Active capability sets (bitmap / surface-commands / large-pointer / GFX caps). The mitm passes mstsc's Connect Initial through verbatim (only patching serverSelectedProtocol/clientRequestedProtocols); we build our own. Next: diff mstsc's caps vs what `protocol.js` builds.

NOTE: mstsc's GFX CAPS_ADVERTISE is RDP-bulk-compressed in c2s (61-byte high-entropy blob, no plaintext capset version constants found); ours is sent uncompressed. Both get CAPS_CONFIRM, so compression itself isn't the gate.

Parser findings (`/tmp/rdpmitm/parse_caps.py` — de-frames TPKT/X224/MCS, isolates drdynvc channel 1007, decodes DVC PDUs incl. v3 0x06/0x07, lists CREATE/CLOSE + GFX PDUs):
- Host streamed mstsc **2163 GFX DVC DATA PDUs** (vs our ~3 frames). mstsc replied with 527 DATA PDUs on GFX (the per-frame 0x0d+0x16 acks).
- **Host streams GFX to mstsc UNCOMPRESSED at the DVC layer** (all DATA/DATA_FIRST, compressed=False). The s2c GFX payloads are ZGFX blobs (descriptor 0xe0 single-segment); v3 compressed DVC (0x06/0x07) is NOT used for the GFX data stream — v3 mattered only for the capabilities handshake.
- Host offers mstsc a **`WebAuthN_Channel`** DVC (id 12/16) that we have not seen handled in our client — worth checking whether the host offers it to us and we reject it.
- drdynvc channelId is 1007 in this capture; GFX dynamic channelId is 7.
