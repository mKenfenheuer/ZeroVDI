## Feature 1 — SSO / one-click connect
- `RDPResourceUserAuthorization` gained `Protected{Username,Password,Domain}` (DataProtection-encrypted, via `RDP/CredentialProtector.cs`, keyring under `DataProtection:KeysDir` default `Data/dp-keys`) + a JSON-column `ConnectionDefaults` (`Models/ConnectionDefaults.cs`: Audio/Clipboard/Microphone/Camera/GfxMode/PerformanceFlags — console-form-shaped, NOT the .rdp-shaped `RdpOptions`).
- Flow (chosen: release-to-browser, NOT zero-knowledge): the VM password is needed in TWO places — gateway NLA/CredSSP AND the browser's inner RDP Client Info auto-logon PDU (`protocol.js clientInfoPdu`). So `HomeController.Console` releases stored creds to the user's own browser over HTTPS (ViewData AutoConnect/Stored*), and `RdpWebSocketController` passes them to `RdpRelaySession` (new `VmCredentials? presuppliedCreds` ctor arg → skips `ReadCredentialsAsync`). `client.js` suppresses the credentials WS frame when `window.RDP_AUTOCONNECT` (else the relay, already bridging, would mis-read it as RDP bytes). Console.cshtml auto-fires the existing login-form submit on load.
- Admin UI: RUA Edit has a SetCredentials/ClearCredentials POST pair (Protected* never form-bound) + a `_ConnectionDefaultsEditor` partial. Edit POST is load-then-mutate (never `Update()` a fresh graph — that would null stored creds).

## Feature 2 — server-side MP4 recording
Architecture: the gateway relays opaque RDP bytes; recording reuses RdpWire's structural decode to EXTRACT media (no pixel decode), then ffmpeg-MUXES (remux, not re-encode) to files. **★ FOUR independent per-track files per recording — `desktop.mp4` / `camera.mp4` (h264 copy) + `audio.m4a` / `mic.m4a` (pcm→aac)** — sharing ONE session-epoch timeline (t=0 = session start) so the web player loads each as its own element and syncs by `currentTime`. Chosen 2026-06-23 (history: two files → ONE combined `session.mp4` w/ 4 tracks → back to four SEPARATE files, because a browser can't render 2 video + 2 audio tracks from one muxed file simultaneously). `RecordingMuxService.MuxVideoFileAsync` remuxes each VFR MKV `-c:v copy -movflags +faststart`; `MuxAudioFileAsync` does `-af adelay=offsetMs:all=1 -c:a aac -movflags +faststart` (faststart = moov before mdat, essential for in-browser seek). Model: `Recording.{DesktopFilePath,CameraFilePath,AudioFilePath,MicFilePath}` (migration `AddRecordingPerTrackPaths` adds Audio/Mic columns; Desktop/Camera reused). On mux FAILURE, `DesktopFilePath` is kept pointing into baseDir so `Delete` can still find the dir. `GetFile(id, track=desktop|camera|audio|mic)` serves one file (range, audio/mp4 for m4a). Old single-file recordings still replay: their `DesktopFilePath` = `session.mp4`, served as track=desktop (desktop+first-audio play natively); other path columns null so the player just omits those streams. Replay view (`Play.cshtml`) = custom 4-stream player: large desktop + small camera PiP (⇄ swap), two `<audio>` (system+mic) toggleable independently, master-clock sync (desktop drives, 500ms drift watchdog re-locks followers), one timeline/scrubber + play/volume/fullscreen + space/arrow keys. CSS/JS inlined (`_Layout` has only a `Scripts` section, no `Styles`).
- `RdpWire/RdpMediaSink.cs`: `IRdpMediaSink` (OnDesktopVideo/OnRemoteAudio/OnMicAudio/OnCameraFrame). `RdpSession(sink, media)` overload. Extraction in `RdpChannels.cs`:
  - Desktop video: GFX `WIRE_TO_SURFACE_1` → strip RFX_AVC420_METABLOCK → H.264 Annex-B. AVC420 (0x0b) clean; AVC444/v2 (0x0e/0x0f) split LC|cb1 word, record MAIN (4:2:0) view only (chroma-aux dropped — v1). **★ This host INTERLEAVES AVC444v2 keyframes with codecId=0x0000 UNCOMPRESSED (and other non-AVC) delta rects.** Recorder must NOT mark the whole recording unsupported on the first non-AVC frame — it skips non-AVC frames and keeps the AVC. `UnsupportedVideoCodec` is computed = `sawOtherCodec && !sawAnyAvc` (audio-only only when NO H.264 ever arrived).
  - **★ Per-frame video timestamps come from the recorder's own monotonic Stopwatch, NOT the GFX wire `START_FRAME.timestamp`** — the wire value is garbage for PTS (observed `[0, 6458553, 0, 6458611, ...]`: an arbitrary host clock interleaved with 0s, 239/742 non-increasing). mkvmerge v2 requires strictly-increasing timestamps (`exit 2: "timestamps that are not ordered"`), so `WriteFrameTs` bumps any ts ≤ previous to previous+1. The relay only sees arrival time anyway. (mkvmerge prints errors to STDOUT not stderr — RunAsync captures both.)
  - Remote sound: rdpsnd is uncompressed PCM (WAVE_FORMAT_PCM only); parse SNDC_FORMATS, emit WaveInfo/Wave2 PCM (legacy two-PDU stitch via session `PendingWave`). **★ Modern Windows carries rdpsnd over the `AUDIO_PLAYBACK_DVC` DYNAMIC channel, NOT the static `rdpsnd` channel** (the static one is advertised but unused for audio). `DispatchDvcPayload` routes `AUDIO_PLAYBACK_DVC` through the same `DecodeRdpSnd` wave-extractor (the DVC payload is a complete SNDPROLOG-framed message). Routing it to the old log-only `DecodeRdpSndInline` = silent desktop audio (was a bug).
  - Mic: audin (AUDIO_INPUT DVC) MSG_SNDIN_DATA(0x06) PCM, c2s. Camera: RDPECAM `RDPGWCam*` device channel — StartStreams(0x0F, s2c) sets NV12 geometry, SampleResponse(0x12, c2s) = raw NV12 frame.
- **Recording is TWO-PHASE (raw capture → background mux), NOT live ffmpeg.** This replaced an earlier live-ffmpeg-via-FIFOs design that deadlocked (ffmpeg probes the video input before opening the audio FIFO; and a video-only session — remote sound off — never launched because launch was keyed on first audio). Current:
  - `RDP/SessionRecorder.cs` (implements IRdpMediaSink): during the session just APPENDS raw elementary streams to files under the recording's base dir — `desktop.h264` (concatenated H.264 Annex-B AUs), `desktop.pcm`, `camera.nv12`, `mic.pcm` — plus a `manifest.json` sidecar (audio PcmFormat, camera WxH/fps, observed codec). No ffmpeg, no pipes, no process during the session → cheap, crash-resilient (partial raws still mux). Plugged into `RdpRelaySession.RdpRecorder` (generalized to take an `IRdpMediaSink` + `NullEventSink`; runs whenever a media sink OR `RDPGW_DUMP_DIR` is set), fed off the relay hot path via the existing bounded-Channel drain task.
  - On session end the controller closes the recorder (writes manifest) and sets `Recording.Status = Processing`.
  - `RDP/RecordingMuxService.cs` (hosted `BackgroundService`, 5s poll): claims `Processing` recordings, reads manifest, runs ffmpeg per output reading REAL files (no FIFO/launch race) — desktop `-r 30 -f h264 -c:v copy` [+ PCM→aac], camera NV12 `-c:v libx264` [+ mic→aac], `-movflags +faststart`. Sets Completed/UnsupportedCodec, DELETES raws on success (keeps them on Failed for retry). Also recovers recordings left `Processing` by a crash.
  - **★ Camera black-frame padding (2026-06-23):** the camera is usually active only for a window in the middle of the session, so its track used to be short (e.g. 13s of a 31s session) and mis-positioned. Fix: camera timestamps are now **session-epoch-relative** (not first-camera-frame-relative), and `SessionRecorder.PadCameraBlack` synthesizes black NV12 frames (Y=0x00, UV=0x80) at a 200ms cadence to fill the lead-in (before the camera ever starts), any mid-session gap, and a trailing pad at Dispose (to the session end). So the camera track spans the whole session; inactive periods render black. `MicOffsetMs` is therefore epoch-relative too (was camera-first-frame-relative).
  - **★ Remote-sound parse fixes (2026-06-23, diagnosed via OnDiagnostic):** SNDC_FORMATS over `AUDIO_PLAYBACK_DVC` parsed as `pcm=0` despite the host advertising 30 formats incl. PCM. TWO bugs: (1) the SNDC_FORMATS preamble is **20 bytes** — `dwFlags(4) dwVolume(4) dwPitch(4) wDGramPort(2) wNumberOfFormats(2) cLastBlockConfirmed(1) wVersion(2) bPad(1)` — I'd parsed it as 19 (dropped `cLastBlockConfirmed`), shifting every AUDIO_FORMAT by one byte so no `wFormatTag` matched PCM(0x0001). (2) **`wFormatNo` in WAVE PDUs indexes the PCM-ONLY agreed list (server-advertised order), NOT the full list** — confirmed against the browser's `rdpsnd.js` (`_deliverWave`: `this.formats[formatNo] || this.formats[0]`, where `this.formats` = the server's PCM subset because the client advertises only PCM). So `EmitRemoteWave` indexes `SndFormats` (PCM-only) with a formats[0] fallback. (I briefly mis-changed this to full-list `Dictionary` indexing — wrong, reverted.) ALSO: the WaveInfo PDU that starts a wave is **msgType 0x02** (`SNDC_WAVE`, body=12B: wTimeStamp(2) wFormatNo(2) cBlockNo(1) bPad(3) Data(4)), and the wave continuation is a bare no-SNDPROLOG PDU (`bPad(4)+Data`) stitched via `s.PendingWave`. (I'd wrongly treated 0x01 as WaveInfo and 0x02 as a no-op.)
  - **★ Mic (audin) works** once `AUDIO_INPUT` DVC is created and DATA(0x06, c2s) flows — confirmed capturing 44100/16/2 PCM.
  - **★ OPEN audio-capture investigation (2026-06-23):** a recording captured desktop video + camera but `DesktopAudio`/`MicAudio` were BOTH null despite audio+mic playing. Video paths (GFX s2c, camera c2s) worked, so the media sink + both feed directions are fine — only the rdpsnd/audin paths produced nothing. Added `IRdpMediaSink.OnDiagnostic(string)` (default no-op) + breadcrumbs from RdpChannels: DVC `create` names, `rdpsnd SNDC_FORMATS` count, `audin msg 0x..`. `SessionRecorder.OnDiagnostic` LogDebug's them deduped-by-prefix. Run a recording with `KSol.RDPGateway:Debug` logging → the logs will show whether `AUDIO_PLAYBACK_DVC`/`AUDIO_INPUT` channels are even created and whether SNDC_FORMATS/wave msgs arrive, to localize the break. (Hypotheses: DVC name mismatch so it never routes to DecodeRdpSnd; or formats negotiated but wave PDUs use an unhandled msgType.)
  - **★ Timing (VFR) — frames have NO inline PTS, the host sends them at DYNAMIC intervals; muxing at any fixed/average rate is wrong (wrong duration + jerky):** SessionRecorder writes a **per-frame timestamp sidecar** (mkvmerge "v2" format: `# timestamp format v2` then one ms-since-first-frame per frame, in order) for BOTH desktop H.264 (`desktop.ts.txt`) and camera (`camera.ts.txt`). The mux applies these with **`mkvmerge --timestamps 0:<ts> <h264>` → VFR MKV (copy, no re-encode)**, then ffmpeg remuxes the MKV `-c:v copy` + PCM→aac → MP4. ffmpeg ALONE cannot do this — it has no per-frame-PTS sidecar input for `-c copy` (verified: per-AU-file concat breaks because non-keyframe AUs lack SPS/PPS). Needs `mkvtoolnix` in the Dockerfile. Camera NV12 is encoded NV12→H.264 elementary first (ffmpeg, order preserved 1:1), THEN mkvmerge timestamps it. Audio still silence-padded via `-af adelay=<offsetMs>:all=1` (offset = firstAudioTs − videoStartTs) so it lands at its real time, not bunched at t=0. RecordingMuxService keeps intermediates (camera.enc.h264, *.vfr.mkv) → deletes always; raws deleted only on success.
- `RecordingStatus` adds `Processing=4`. ffmpeg still needed in the Dockerfile (`coreutils` no longer required — no mkfifo).
